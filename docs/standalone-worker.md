# Run a standalone worker

The `conductor-worker` command is a real, long-running local process. It saves
you from manually sending worker registration, heartbeat, resource-report, and
lease-polling requests one by one.

In plain English: the API is the coordinator; this command is one person doing
the regular check-in and asking, “is there a job for me?”

## What it does today

After it starts, one worker process:

1. registers its stable worker name and a fresh process-instance ID;
2. sends heartbeats while it is alive;
3. measures host and process CPU/RAM with `psutil` and reports a snapshot;
4. polls for one compatible job at a time;
5. starts and executes a leased job through the existing API; and
6. enters draining state when you press `Ctrl+C`, so it accepts no more work.

The default worker is deliberately **single-slot**. It never advertises two
parallel execution slots while its loop can only run one job at a time.

## Run it locally

Use three terminals from the repository root.

Terminal 1 starts the control plane:

```bash
conductor-api
```

Terminal 2 starts a worker that can generate text. The default URL already
points to the local API, so `--api-url` is optional:

```bash
conductor-worker --worker-id laptop-worker --task text.generate
```

Terminal 3 registers the deterministic fixture model and submits a job:

```bash
conductor models register --file examples/fixture-model.json
conductor jobs submit --file examples/fixture-job.json --idempotency-key standalone-worker-demo-1
conductor jobs list
```

The worker polls, claims the job, and asks the API to execute it. Refresh the
dashboard or run `conductor jobs list` to see the durable result. The worker
also creates resource snapshots that appear in the worker detail view.

Press `Ctrl+C` in Terminal 2 to stop. The process first stops polling, then
sends a final **drain** request. Draining means “do not give me new jobs.”

## Useful options

```text
--worker-id NAME                  Stable logical name, for example laptop-worker
--instance-id NAME                Exact process identity; generated by default
--task TASK                       Supported task; repeat this option for more tasks
--heartbeat-seconds SECONDS       Default: 5
--resource-report-seconds SECONDS Default: 5
--poll-seconds SECONDS            Default: 1
```

The generated instance ID looks like `process-...`. Each restart gets a new
one, which lets the control plane reject a late message from the old process.
See [`workers.md`](workers.md) for the fuller explanation.

## What CPU and RAM numbers mean

`psutil` asks macOS for measurements. Each snapshot contains:

- host CPU: how busy the whole laptop is;
- host available memory: memory the operating system can give new work soon;
- process CPU: CPU used by this `conductor-worker` process; and
- process memory: RAM currently held by this process.

The first process-CPU value can be `0`. That is normal: CPU percentage needs a
short time interval to compare “work done before” and “work done after.” Later
reports have a real interval to measure.

## Important current boundary

This is an honest intermediate step, not a hidden claim of fully remote model
execution. The standalone process owns the **worker protocol** and telemetry,
but the current `/execute` API endpoint still calls `RuntimeManager` inside the
FastAPI control-plane process.

```text
standalone worker: register → heartbeat → report resources → lease → start
                                                               ↓
control-plane API:                                      /execute → runtime adapter
```

Moving the runtime adapter and loaded model instance into the standalone worker
is a later phase. That change needs a result-reporting protocol and careful
failure recovery, so it deserves to be designed rather than implied.

## Code path to read

1. `backend/src/conductor/workers/runner.py` contains the process loop and
   `psutil` sampler.
2. `backend/src/conductor/cli/client.py` provides the small HTTP client used by
   both terminal tools.
3. `backend/src/conductor/api/workers.py` receives worker protocol requests.
4. `tests/test_worker_runner.py` is a small executable example of registration,
   periodic reports, leasing, execution, and graceful drain.
